# 📉 ChurnGuard — Telecom Customer Churn Prediction

ChurnGuard is an end-to-end machine learning project that predicts which telecom customers are likely to churn, so retention teams can act *before* they leave — not after.

Using billing, usage, network-quality, and demographic data, ChurnGuard identifies at-risk, high-value customers and surfaces the behavioral signals driving that risk (e.g. a quiet drop in usage, an aging handset, rising customer-care contacts). The project also ships a lightweight web app so anyone can plug in a customer's details and get an instant churn probability.

## 🎯 Problem & Objective

Customer churn is a direct source of revenue leakage. Exploratory analysis on this dataset shows that churners tend to be **active, high-value spenders** (average monthly revenue ≈ $58) who show a **silent usage drop** (average change in monthly usage ≈ −23 minutes) combined with an **aging device** (average equipment age > 420 days) shortly before they leave.

The goal of this project is to frame churn as a binary classification problem and build a model that flags these customers early — enabling proactive, targeted retention actions (e.g. device upgrade offers) instead of blanket, budget-draining campaigns.

## 🗂️ Dataset

The data comes from two merged sources, joined on `Customer_ID`:

- **`Record.csv`** — usage, billing, and network-quality metrics (call minutes, revenue, dropped/blocked calls, overage, roaming, customer-care contacts, etc.)
- **`Client.csv`** — customer and account attributes (tenure, handset details, demographics, plan/subscription info)

Target variable: `churn` (binary — churned vs. stayed).

## 🔧 Approach

1. **Exploratory Data Analysis (EDA)** — missing-value patterns, class balance, and univariate/bivariate relationships between churn and key usage, billing, and equipment features.
2. **Feature Engineering** — beyond the ~90 raw features, 15 engineered features were derived to capture financial pain, device staleness, usage momentum, and technical frustration, including:
   - `total_overage_charge`, `overage_intensity` — cost-shock indicators
   - `device_generation_gap`, `never_upgraded`, `handset_depreciation_index`, `phones_per_year` — hardware staleness signals
   - `revenue_utilization_index`, `relative_mou_momentum`, `relative_rev_momentum`, `silent_drop_indicator` — usage/spend momentum
   - `call_failure_rate`, `voice_drop_ratio` — network-quality frustration
   - `data_usage_ratio`, `peak_usage_ratio`, `inactive_subs_count` — usage pattern and account hygiene
3. **Modeling** — a stratified train/validation/test split (70/15/15), with five candidate models trained and compared using dedicated preprocessing pipelines per model family:
   - Logistic Regression (median/mode imputation, scaling, one-hot encoding)
   - Random Forest (median/mode imputation, ordinal encoding)
   - XGBoost & LightGBM (native missing-value handling, ordinal-encoded categoricals)
   - CatBoost (native categorical + missing-value handling)
4. **Evaluation** — models are compared on validation ROC-AUC/F1, with a single, final held-out test-set evaluation for the winning model to avoid test-set leakage.
5. **Selection** — the best-performing model (by test ROC-AUC) is serialized with `joblib` as `best_churn_model.pkl`.

## 🚀 Deployment

A separate Colab-ready notebook loads `best_churn_model.pkl` and spins up a [Gradio](https://www.gradio.app/) web app. Users fill in a short, plain-English form covering the ten strongest churn signals (tenure, revenue, usage, plan charge, usage trend, customer-care contacts, handset price, and line counts) and get back a churn/stay prediction with a probability. Any field left blank is passed to the model as a true missing value — handled natively, with no fabricated defaults — and the same 15 engineered features are recomputed on the fly from whatever raw values are provided.

## ▶️ Getting Started

1. **Train the model:** open `churnguardv2.ipynb` in Google Colab, mount your Drive with `Record.csv` and `Client.csv`, and run all cells. This produces `best_churn_model.pkl`.
2. **Try the app:** open `churnguard_deployment_colab.ipynb` in Colab, run all cells, upload `best_churn_model.pkl` when prompted, and open the public Gradio link from the last cell.
